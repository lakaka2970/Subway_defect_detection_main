# 2 — 后端开发方案

> 涵盖：Java 21 + Spring Boot 3、（地面端微服务 / 车载端单体）、数据模型、接口设计、部署

---

## 0. 架构总则：两个后端项目

本系统后端是**两个独立工程**，共享同一套公共库与数据模型，但部署形态、治理方式不同：

| 工程 | `inspection-ground-server`（地面端） | `inspection-onboard-server`（车载端） |
|------|--------------------------------------|----------------------------------------|
| **架构** | **微服务**（Spring Cloud + Gateway） | **单体**（单 JAR，内嵌全部模块） |
| **运行** | 多服务进程，可独立扩缩容 | 一个 Spring Boot 应用，零外部注册中心 |
| **部署** | 单机 / 集群两种模式 | 工控机本地，完全离线 |
| **服务发现** | Nacos / Spring Cloud LoadBalancer | 无（模块内方法直接调用） |
| **数据库** | MySQL 主从 | MySQL 单机（或内嵌） |
| **缓存/队列** | Redis 哨兵集群 | Redis 单机 |
| **AI 服务** | FastAPI（多 GPU 集群，内网/Nginx） | FastAPI（本地 `localhost:8001`） |
| **目标** | 高吞吐批量分析、专家复核、报表、权限审计 | 现场轻量初判、离线可用、强稳定 |

> **复用策略**：两工程共用 `common-*` 公共库与 `domain-model`（实体/DTO/枚举/缺陷字典），保证缺陷与任务数据在双端拷贝同步时**字段与语义完全一致**。业务逻辑通过模块化拆分，地面端以「微服务」边界部署，车载端以「模块」形式内嵌进单 JAR。

## 2. 项目结构（两个工程）

### 2.1 公共库（两工程共享，独立 Maven 模块）

```
inspection-backend-commons/             # 发布到私服，被两个工程依赖
├── common-core/                        # 工具、常量、异常、统一响应 R<T>
├── common-security/                    # Sa-Token 配置、权限注解 @SaCheckPermission
├── common-web/                         # Web 配置（CORS/拦截器/全局异常处理）
├── common-storage/                     # MinIO 操作封装
└── domain-model/                       # 实体 / DTO / 枚举 / 缺陷字典（双端一致的根基）
```

### 2.2 地面端 — `inspection-ground-server`（微服务）

```
inspection-ground-server/
├── gateway/                            # Spring Cloud Gateway（统一入口 + 鉴权前置）
├── service-task/                       # 任务管理服务      /api/v1/task/*
├── service-rawdata/                    # 原始数据服务      /api/v1/rawData/*
│   └── service/{RawDataService, StoragePathService, XmlMetadataService}
├── service-defect/                     # 缺陷管理服务      /api/v1/defect/*
├── service-ai-scheduler/               # AI 分析调度服务   /api/v1/aiTask/*
│   ├── service/{AiTaskScheduler, AiProgressPusher, AiResultHandler, CheckpointService}
│   └── client/DlServiceClient.java     # 调用 FastAPI
├── service-auth/                       # 鉴权与审计        /api/v1/auth/* , /api/v1/audit/*
├── service-report/                     # 报表统计          /api/v1/report/*
│   └── service/{StatisticsService, ExcelExportService, WordExportService}
├── service-sync/                       # 双端数据同步（接收车载数据包）
└── docker-compose-ground.yml           # 集群部署编排
```

### 2.3 车载端 — `inspection-onboard-server`（单体单 JAR）

```
inspection-onboard-server/              # 一个 Spring Boot 应用，端口 8080
└── src/main/java/.../
    ├── OnboardApplication.java         # 单一启动类，内嵌以下全部模块
    ├── module/task/                    # 任务管理（同套实体，精简接口）
    ├── module/rawdata/                 # 原始数据 + 三级目录 + info.xml
    ├── module/defect/                  # 缺陷初判与现场复核
    ├── module/ai/                      # AI 调度（本地 FastAPI）+ 断点续跑
    │   └── CheckpointService.java      # 进程崩溃/断电后从记录点续跑
    ├── module/sync/                    # 导出数据包（移动硬盘交接）
    └── module/auth/                    # 精简鉴权（现场分析员/管理员）
# 不引入 gateway / 报表 / 完整权限管理；通过 Maven profile 裁剪模块
```

> 同一份 `RawDataService`、`DefectService` 业务代码可被两工程复用：地面端封装为独立 `@Service` 微服务，车载端作为内部 `module` 直接方法调用。差异仅在装配（微服务 vs 单体）与基础设施配置。

## 5. AI 分析调度流程

```
前端发起分析
     │
     ▼
POST /api/v1/aiTask/start  ← 携带 taskId
     │
     ▼
AiTaskScheduler:
  1. 校验任务状态 → 更新为 "analyzing"
  2. 查询该任务的 raw_data 列表，生成待处理队列
  3. 根据来源（车载/地面）选择模型配置
  4. 将分析任务推入 Redis List: ai:queue:{onboard|ground}
     - 每项: { "analysisId": "xxx", "imagePath": "...", "rawDataId": 123 }
     │
     ▼
异步消费者（Spring @Async / 虚拟线程）
  while 队列不空:
      取 imagePath → 调用 DlServiceClient.infer(imagePath)
      → 解析结果 → 写入 t_defect 表
      → 更新 t_raw_data.analysis_status
      → 通过 WebSocket 推送进度
      → 队列为空时，更新 t_task.status = "completed"
```

### 5.1 调用 DL 服务

```java
// services/service-ai-scheduler/src/main/java/.../client/DlServiceClient.java

@HttpExchange("/api/dl")
public interface DlServiceClient {

    @PostExchange("/infer")
    InferResponse infer(@RequestBody InferRequest request);

    @GetExchange("/model/health")
    ModelHealthResponse health();

    @PostExchange("/model/load")
    LoadModelResponse loadModel(@RequestBody LoadModelRequest request);
}

// InferRequest
record InferRequest(
    String imagePath,           // 图像在 MinIO 的相对路径
    String modelType,           // "onboard" | "ground"
    String modelVersion,        // 模型版本号，如 "yolov11s-v1.2"
    Double confidenceThreshold, // 置信度阈值（可选，覆盖默认值）
    Integer sliceSize           // 切片尺寸（可选）
) {}

// InferResponse
record InferResponse(
    String imagePath,
    List<DefectResult> defects,
    Integer processingTimeMs
) {}

// DefectResult
record DefectResult(
    String defectType,
    Double confidence,
    Double boxX, Double boxY, Double boxW, Double boxH,
    String boxCoordType  // "normalized" | "pixel"
) {}
```

### 5.2 断点续跑与崩溃恢复（车载端重点）

> 依据《模糊需求开发技术交流》答复：「每次分析都会记录结果，下次开启从记录点继续」。

- **逐张落盘**：每处理完一张图像即写入 `t_defect` 与更新 `t_raw_data.analysis_status='completed'`，**不做整批事务**，保证已写入数据持久。
- **检查点**：以 `t_raw_data.analysis_status` 作为天然检查点。重启/断电/进程被杀后，调度器只挑选 `analysis_status IN ('pending','analyzing')` 的图像重新入队（`analyzing` 视为中断，重算该张）。
- **续跑触发**：
  - 车载端启动时自动扫描未完成任务并续跑（无需人工整段重算）。
  - 用户「暂停→恢复」从暂停点继续。
- **无回滚语义**：依据答复「不存在回滚」，已提交结果不做批量回退；如需纠正按单条缺陷状态流转处理。
- **保留期起算**：异常中断重算后，「离线数据保留 7 天」起算点**重新计算**；失败任务占用空间**计入**磁盘配额。

### 5.3 本地存储异常处理（车载端）

| 场景 | 处理策略 |
|------|----------|
| 数据盘不可用/只读 | 不创建新任务、不采集（采集软件职责）；分析端给出明确告警并停机等待 |
| 磁盘空间不足 | 采集软件按时间滚动删除最早数据至阈值；分析端检测到空间不足暂停新分析 |
| 单张图像损坏 | DL 返回 `DL_IMAGE_UNREADABLE` → 标记 `skipped`，继续下一张，不中断任务 |

## 6. 双端数据同步

### 6.1 同步时机

| 触发方式 | 场景 |
|----------|------|
| **自动** | 车载端联网→检测到 `sync_status='pending'` 的数据→自动推送 |
| **手动** | 用户在地面端或车载端点击"同步"按钮 |
| **定时** | 地面端每 30 分钟检查不一致数据并校正 |
| **移动硬盘** | 车载端导出数据包→拷贝→地面端导入 POST `/api/v1/rawData/upload` |

### 6.2 同步冲突处理

当双端同时修改同一数据（如同一缺陷）时，采用 **"时间戳优先"** 策略：

```sql
-- 同步时带上时间戳比较
UPDATE t_defect
SET status = #{newStatus}, updated_at = #{newUpdatedAt}
WHERE id = #{id}
  AND updated_at < #{newUpdatedAt};  -- 仅当新数据更新时覆盖
```

冲突记录写入 `t_sync_conflict_log` 表，便于人工介入。

## 7. 文件存储方案

### 7.1 MinIO 目录结构

遵循 SRS《附件-1ver02》4.2.2 规定的**三级目录结构**：第一级线路名称、第二级区站名称、第三级支柱号。

```
bucket: inspection-data/
├── {line_name}/                       # 一级：线路名称（如 "2号线"）
│   └── {station_area}/                # 二级：区站名称（如 "鼓山-南门兜"）
│       └── {pillar_code}/             # 三级：支柱号（如 "P125" / "K2249449_23"）
│           ├── info.xml               # 元数据（自包含、可解析）
│           ├── original/              # 原始图像
│           │   ├── front_left.jpg
│           │   ├── front_right.jpg
│           │   └── ...
│           ├── thumbnails/            # 256px WebP 缩略图
│           └── tiles/                 # DZI 瓦片
│               └── {image_name}/
│                   ├── 0/             # Level 0 (最高分辨率)
│                   ├── 1/
│                   └── ...
├── templates/                         # 报表模板
└── models/                            # AI 模型文件（由 DL 团队管理）
```

### 7.1.1 info.xml 字段规范（依据 SRS 4.2.3）

| 字段类别 | 字段 |
|----------|------|
| 基础信息 | 缺陷编码、公里标、支柱号、检测时间、帧号、车速 |
| 几何参数 | 导高、拉出值、双支高度差、水平距离 |
| 定位信息 | 坐标精度、经纬度 |
| 关联信息 | 线路、区站、关联缺陷列表（缺陷编码 + 类型 + 坐标） |

> 由 `XmlMetadataService` 在数据入库时生成、查询时解析；字段与 `t_raw_data` / `t_defect` 一一映射，保证「采集—分析—复核」全链路可追溯。

### 7.2 图像预处理流水线

```
原始图像入库 → 后端触发异步任务：
  1. 生成缩略图（256×256 WebP） → MinIO thumbnails/
  2. 生成 DZI 瓦片（调用 vips 命令行或 Java lib） → MinIO tiles/
  3. 更新 t_raw_data 的 thumbnail_path 和 tile_path
```

**技术选型**：使用 `libvips`（通过 JNI 调用或命令行）生成 DZI 瓦片，速度比 ImageMagick 快 5-10 倍。

## 10. 虚拟线程利用

Java 21 虚拟线程特别适合本项目的 I/O 密集型场景：

```java
// AI 分析调度：每张图像的推理是 I/O 等待密集型
@Bean
public Executor aiTaskExecutor() {
    return Executors.newVirtualThreadPerTaskExecutor();
}

@Async("aiTaskExecutor")
public void processImage(String imagePath) {
    // 调用 DL 服务（HTTP 阻塞等待）→ 解析结果 → 入库
}
```

注意事项：
- 虚拟线程不要用于长时间 CPU 密集型计算
- JDBC 驱动需确认兼容虚拟线程（MySQL Connector/J 8.2+ 已兼容）
- 避免在虚拟线程中使用 `synchronized` 块（用 `ReentrantLock` 替代）

## 11. 两个后端工程差异对照

| 维度 | 车载端 `inspection-onboard-server`（单体） | 地面端 `inspection-ground-server`（微服务） |
|------|--------------------------------------------|----------------------------------------------|
| **架构形态** | 单 JAR，模块内嵌、方法直调 | 多微服务 + Spring Cloud Gateway |
| **服务发现/网关** | 无 | Nacos/LoadBalancer + Gateway |
| **数据库** | 单机 MySQL（可内嵌） | MySQL 主从 + 集群 |
| **缓存/队列** | 单机 Redis | Redis 哨兵集群 |
| **存储** | 单机 MinIO | MinIO 分布式集群 |
| **AI 模型** | 轻量模型（本地 FastAPI `localhost:8001`） | 完整模型（多 GPU 集群） |
| **断点续跑** | 重点能力（崩溃/断电自动续跑） | 支持，但以批量吞吐为主 |
| **报表/权限管理** | 精简（不含完整报表、复杂权限） | 全功能（Excel/Word/PDF、动态 RBAC、审计） |
| **数据同步** | 导出数据包（移动硬盘）→ 主动推送 | 接收 → 校验 → 时间戳优先合并 |
| **网络** | 完全离线运行 | 在线，集群高可用 |
| **打包/部署** | 原生 JAR + 随车工控机 | Docker / Docker Compose / K8s |

> 共用：`inspection-backend-commons`（含 `domain-model`），二者实体、枚举、缺陷字典、统一响应、错误码完全一致，详见《4-接口规范标准》。
