## 1. 行业实践调研结论（他人经验摘要）

以下结论来自公开标准、专利与开源项目检索，是本方案的直接依据：

### 1.1 标准与规范

- **《城市轨道交通车载轨道高速巡检系统技术规范》（江苏省地方标准）**：巡检系统应由**定位子系统、高清成像子系统、智能识别子系统、数据信息处理子系统**组成；设备外轮廓符合 GB 146.1 车辆限界；应支持双向检测且结果不受速度方向影响；**曝光时间有上限公式**（防运动模糊），**光源补光时长应大于相机曝光时长但避免过曝**；单张图像识别时限与采样间隔、行数的约束关系。
- **《隧道内轨道式病害监测机器人》团体规程**：不应侵入隧道建筑限界，与带电设施保持安全距离；作业环境应设标志、清除非设计工况障碍；机器人应由专人负责定期维护。

### 1.2 里程定位（专利与工程先例）

- **编码器外触发行标做法**（车载轨道巡检装置发明专利 CN202110512385）：**里程编码器脉冲直接外触发相机**，以当前里程值命名图像 → 缺陷像素坐标天然携带里程信息，复核可直接按里程找现场。
- **RFID 校正先例**（南京地铁网轨检测车）：编码器定位受轮径磨损、曲线影响存在累积误差；GPS 隧道内不可用、人工对公里牌夜间不可行。本项目**不加装标签**，故该先例转化为"**用既有视觉标牌充当离散校正源**"的设计动机。
- **加减速伪影教训**（电客车挂载巡检专利 CN202511214633）：用速度信号换算触发频率有延迟，加速段图像压缩、减速段拉伸 → 自走行小车自带高分辨率编码器做**定距外触发**从根源规避。
- **打滑教训**（隧道机器人工程实践总结）：伺服电机内置编码器反馈**不能单独用于定位**——轨道异物导致驱动轮打滑时位置失真，必须引入外部绝对参考离散校正。
- **融合定位研究**（地铁隧道综合检测车）：编码器 + 视觉融合 + 精度校正，区间精度可达 10 cm，300 m 直线段相对误差 ≤0.06%。

### 1.3 成像与同步

- **多相机布局先例**（隧道轨道检测机器人实用新型 CN202020247376）：轨道面相机 ×2 斜向下 + 拱顶相机 ×2（旋转机构仰拍）+ 补光灯及散热器——**拱顶仰拍通道正是本项目弓网检测所需形态**。
- **Autoware 相机集成指南**：GMSL2（超低延迟 + 同轴 FSYNC 触发）/ USB3（免驱但触发需附加设备）/ GigE（长距传输、GenICam 参数可控）三路线权衡；GigE 必开 jumbo frame（MTU 9000）防丢帧。
- **ROS2 开源组件**：`ros-drivers/flir_camera_driver`（同一硬件触发脉冲的多相机帧赋予相同时间戳）、`FraunhoferIOSB/camera_aravis2`（GenICam GigE/USB3，Humble 验证，PTP 支持）、`tier4/sensor_trigger`（Jetson GPIO 触发发生，PTP 秒首相位对齐、CPU 绑核提升时序稳定性）。
- **PTP 踩坑**（Spinnaker 驱动文档实证）：相机运行一段时间后可能拒绝接受 PTP 主钟（卡在 LIS 状态），需重新上电；**主时钟必须先于相机启动**。

### 1.4 自动驾驶 / VLA 技术现状（2025–2026）

- **机器人操作域 VLA**：OpenVLA（7B，Open X-Embodiment 970k 轨迹预训练，LoRA 参数高效微调）、Physical Intelligence **π0 系列**（OpenPi 开源训练框架，万小时级真机数据预训练）、**NVIDIA Isaac GR00T N1.x**（双系统架构：VLM 慢思考 + 扩散动作头快执行；官方工作流 = 遥操作采数 50–100 条/任务 → LeRobot 格式微调 → PolicyServer 部署）。
- **自动驾驶域 VLA**：UniDriveVLA（小米，Mixture-of-Transformers 三专家解耦"理解/感知/规划"，Qwen3-VL 骨干，nuScenes/Bench2Drive SOTA）、OpenDriveVLA（AAAI 2026，0.5B 轻量检查点已开源）、OneVL（latent CoT 兼顾推理质量与时延）。共同趋势：**VLM 语义理解专家 + 几何感知专家 + 动作规划专家解耦**。
- **对本项目的启示**：轨道约束场景的动作空间是一维速度曲线 + 离散事件决策（走/停/道岔），远比开放道路简单——**完整 VLA 端到端驾驶属过度设计且难以安全认证**；但 VLM/VLA 的正确用法是（a）语义层增强（报告生成、异常描述、自然语言任务接口）、（b）作为研究储备的数据引擎闭环。详见 §8。

## 3. 运动控制与自动驾驶技术栈

### 3.1 运动基本参数

| 参数 | 建议值 | 说明 |
|------|--------|------|
| 巡航速度 | 按 4h 作业量反推：`v_cruise = 2×L_route / 4h`（示例 L=20km 往返 → 10km/h 上限档，实际建议 3–8 km/h 档位化） | 同时满足 §4.3 曝光约束 |
| 弯道/道岔区 | ≤1.5 km/h 或步进 0.2 m/步 | 防成像模糊与道岔卡阻 |
| 加速度 | ≤0.3 m/s² | 防机构共振、测量轮跳轨 |
| 制动裕量 | v(km/h)÷3.6 × 1.5s 反应 + 摩擦距离，再 ×2 冗余 | 隧道机器人实践：30 km/h 需 ~5 m 制动，本项目低速等比缩放 |

### 3.2 里程计

- **独立测量编码器装于非驱动测量轮**（恒定下压力），4 倍频/鉴向/光耦去抖；
- 双编码轮互差 >阈值 → 打滑标记，该段降置信（腾讯云隧道机器人项目实证驱动轮编码器不可单独信任）；
- 图像命名携带 `[线路][行别][区段号][里程mm][帧号]`，缺陷报告直接输出区段+里程。

### 3.3 视觉定位：区段标号牌锚点 + 编码器航位推算

```
高频连续:  编码器积分 s(t)、v(t)
              ↑ 每 N m 或每帧做一次
低频锚点:  标号牌相机 → 检测(YOLO) → OCR(PaddleOCR/自训) → [区段号, 里程]
              ↓
融合:      s_anchor = OCR里程 → 重置/比例修正编码器累计误差(最小二乘滑窗)
兜底:      结构特征里程计 —— 电缆支架/消音板缝等等间距结构做视觉测距,
           在两个标牌之间抑制编码器漂移
```

**精度预算**（关键工程账）：

```
设标牌间距 D=1000m, 编码器相对误差 ε=0.15%(含打滑残差):
  区间末端最大漂移 ≈ 1.5m —— 满足"定位到区段"的需求;
  若 D=2000m 且 ε 劣化至 0.5% → 10m, 必须启用结构特征里程计兜底。
```

- **首跑建图（route teaching，工业 AMR 成熟模式）**：首次试巡由人工随车标注每个标牌的精确里程与图像特征 → 生成线路特征地图；后续运行将实时标牌 OCR 结果与地图匹配（容错编辑距离，防 OCR 误读一位数字导致整体错位）。
- **标牌识别可靠性三防线**：① 出库自检时验证 OCR 流水线（预置样本图）；② 运行中 OCR 置信度低于阈值不采纳、继续航位推算并标记"待校正段"；③ 连续 2 个预期锚点未出现 → 停车自检（防止跑错线/漏检导致的系统性错位）。

## 4. 弓网成像子系统（相机向上拍摄）

### 4.1 相机布局（仰拍阵列）

| 通道 | 安装位 | 视场指向 | 覆盖目标 |
|------|--------|---------|---------|
| CAM-U1/U2/U3… | 车体前/中部升降桁架，斜向上 30–60° | 刚性接触网悬挂面（汇流排+悬吊装置+定位线夹）或柔性网（承力索/接触线/腕臂） | 16 类缺陷：螺母缺失/松动、销钉缺口、绝缘子破损、吊弦不受力等 |
| CAM-F（可选） | 前向低帧率 | 线路前方 + 标号牌 + 障碍 | 复用于 marker_reader 与 obstacle_guard |

- 刚性网悬挂点沿隧道顶连续分布，柔性网在站间/车辆段区段——**两种形态的焦距/俯仰配方不同**，按区段切换 profile（任务配方 YAML）；
- 目标高度约 4–4.5 m（隧道刚性网），相机到目标距离短，宜用中等焦距定焦 + 大景深光圈（F5.6–F8）；
- 是否沿用既有"127MP 超高分幅拼接"模式取决于业主对 GSD 的验收口径（§0.1-Q5）；无论哪种，**定距触发 + 里程命名机制不变**。

### 4.2 触发与同步

```
测量编码器 ─▶ trigger_hub(MCU/FPGA, 硬件层)
               ├─ 定距逻辑: 每 Δs 米发一个曝光触发脉冲 ─▶ 全部仰拍相机 Line0 并联
               ├─ 同脉冲选通 LED 仰拍补光灯(脉宽>t_exp, 占空比<10%)
               └─ 里程锁存随帧上传 Jetson(软件侧一一绑定)
时间基准: 车载 ptp4l(GM=主控机), 主时钟先于相机启动(PTP LIS 坑预防);
         收工回传后用库内 NTP 校正绝对时刻。
```

- `Δs = H_pix × GSD × (1−重叠率)`；悬挂点间距通常 ~2–4 m，建议 Δs 取悬挂点间距的整数分之一，使每挂点落帧相位稳定；
- 弯道段自动 `Δs' = Δs/4`（曲率半径小、网面横向摆动大）。

### 4.3 拍摄参数控制

**运动模糊约束**：`t_exp ≤ GSD / v`（例：GSD=1 mm、v=1.39 m/s → t_exp≤0.72 ms≈1/1400s）。

**仰拍特有的照明难点与对策**：

| 问题 | 根因 | 对策 |
|------|------|------|
| 汇流排镜面眩光 | 铝合金汇流排表面定向反射 | 灯具偏轴布置（入射角≠反射角指向相机）、加挡光板、偏振片（可选） |
| 隧道顶积尘降低照度 | 长期免维护环境 | 光通量按 2× 余量设计 + 在线亮度闭环自动调增益 |
| 频闪条纹 | PWM 补光与曝光交互 | 灯具直流恒流瞬态点亮（非 PWM 调光）或同步锁相 |
| 悬挂点背光阴影 | 单侧打光 | 双侧对称补光 + 柔光 |

**参数自适应闭环**（online_qc，CPU 即可）：直方图均值→增益步进；Laplacian 方差→模糊段标记并入复拍队列；触发-帧对账→漏帧段标记；白平衡出库前锁定禁自动。所有参数按区段配方管理，途中仅允许受限微调。

## 5. 运行阶段与状态机

### 5.1 总体作业流程

```
[0 出库准备] → [1 上线装载] → [2 正向巡检] → [3 道岔/换轨] → [4 续段巡检] … → [5 收工拔盘]
                                     ↑______________循环(按当日区段计划)______________|
```

| 阶段 | 关键动作 | 出口条件 |
|------|---------|---------|
| 0 出库准备 | 自检（相机/灯/编码器/OCR 流水线/急停回路/存储压测）；加载区段配方；PTP 域建立 | 全绿 |
| 1 上线装载 | 人工上轨 → 四轮贴轨确认 → 手柄遥控试走 5 m | 试走正常 |
| 2 正向巡检 | 定距采集常开；标牌锚点校正；在线质检 | 到达道岔预告点 / 区段终点 / 4h 倒计时阈值 |
| 3 道岔/换轨 | 见 §5.3 子流程 | 上轨确认 |
| 4 续段巡检 | 同阶段 2（新区段配方切换：焦距/俯仰/Δs/灯亮度） | 当日计划完成 |
| 5 收工拔盘 | bag 分卷封包校验(MD5) → 盘位卸载动画/指示灯 → 提示拔盘 → 拔盘交地面端全量推理 | 数据完整性校验通过 |

### 5.2 运行子状态机（走/停决策表）

```
IDLE→SELF_TEST→TELEOP→PATROL ⇄ TURNOUT_PASSING
PATROL 异常分支:
  ├─障碍物→ OBSTACLE_STOP(声光警示, 遥控确认后继续)
  ├─急停/防撞条→ ESTOP(硬件断电制动, 物理复位+重新自检)
  ├─标牌丢失≥2→ LOC_LOST_STOP(停车自检)
  ├─电源异常(欠压/掉电预警)→ SAFE_HALT(受控停车等待恢复)
  ├─相机掉线/写速不足/余量<10%→ 停车自愈(lifecycle 重启), 失败提前收工
  └─温度超限→ 降速/冷却
```

### 5.3 道岔通过子流程（单线单向换轨核心难点）

```
预告(台账里程−20m) → 降速爬行 → 停车于岔前定位点
  → 岔尖状态核验: 视觉比对岔尖开口 vs 台账期望开通方向
      ├─一致 → 步进通过(0.2m/步, 全程监测牵引电流突变)
      │         → 过岔后直股/侧股贴合确认(横向位移传感器/视觉)
      │         → 恢复巡航, 编码器里程接续
      └─不一致或不确定 → 停车等待人工处置(手柄遥控引导或人力推行过岔)
                        ※ 无网络条件下不允许自主尝试变岔
```

- 道岔台账（里程/岔向/常态开通位）出库前载入并双人复核；
- 过岔全程 blackbox 高频记录（电流、位置、时刻），事后可审计。

### 5.4 弓网供电适应性（重点）

| 场景 | 控制程序行为 |
|------|-------------|
| **分段绝缘瞬时断电**（数十~数百 ms） | 硬件侧 DC 缓冲/UPS 穿越（既有设备范畴）；软件侧 power_guard 监测母线电压，<阈值即受控停车冻结状态 |
| **意外整机断电重启** | systemd 引导 → mission_manager 读取 checkpoint（最后有效里程/区段/采集进度）→ 自检通过后提示"续扫/终止"，禁止静默续跑 |
| 电压波动/浪涌 | 宽压容忍由硬件保证；软件记录电压曲线供事后关联分析（如图像坏帧与电压跌落的相关性） |
| 收工断电顺序 | 先 umount 盘位、封卷 bag、blackbox flush，再提示允许切断弓网电源 |

> 设计原则：**把弓网供电当作"随时会消失的电源"对待**。checkpoint 写入频率 ≥ 每 50 m 或每次状态迁移，写入介质为板载 eMMC（非拔盘位）。

## 8. 自动驾驶系统架构详设（借鉴 Autoware）

> 结论先行：**生产主线采用"借鉴 Autoware 分层架构的自研轻量栈"**。Autoware 是目前最成熟的开源 ROS2 自动驾驶软件栈，但其道路场景假设（Lanelet2 高精地图、LiDAR NDT 定位、横向转向控制、开放交通流）对本项目过重；我们**移植它的架构模式、接口契约与关键算法思想**，替换为轨道约束场景的一维实现。VLM/VLA 作为语义增强与研究储备在 §8.11/§8.12 分层引入。

### 8.1 借鉴边界：取什么、舍什么、为什么

**取（架构模式与接口契约）：**

| Autoware 模式 | 本项目对应 | 收益 |
|--------------|-----------|------|
| 六层流水线 Sensing→Localization→Perception→Planning→Control→Vehicle Interface | 同构保留（§8.3 映射表） | 职责单一、可独立测试替换 |
| Planning 三级分解：Mission(Route)→Behavior(Path+停止约束)→Motion(Trajectory)，接口逐级收窄 | 同构保留，全部一维化 | 道岔/返航/障碍等新增行为只加插件不动主干 |
| **behavior_velocity_planner 场景模块插件机制**（继承 `scene_module_interface.hpp`，`default_preset.yaml` 启停） | `stop_point_manager` 插件框架：ObstacleStop/TurnoutStop/WindowTimeReturn/LocLost/RecapSlowZone 五个插件 | 新停车规则 = 写一个插件类 + preset 注册，不改核心 |
| **StopReasonArray 上报**（每次减速/停车给出结构化原因） | 同构保留，写入 blackbox | 事后审计"当时为什么停"有据可查 |
| **Route/Path/Trajectory 三级消息契约**（Route=拓扑序列不含几何；Path≈粗路径点+可行驶域；Trajectory=0.1s 间隔位姿+速度+加速度，供控制跟踪） | 一维化：Route=区段/道岔序列；Path1D=里程区间+限速包络；Trajectory1D=(s,v,a,t) 序列 | 接口稳定后各模块可并行开发、独立仿真 |
| **trajectory_follower 横纵向分离设计**（基类接口派生算法） | 只留纵向速度控制器（横向由导向轮机械保证），但保留接口抽象便于未来差速纠偏 | 低速场景混合优化无收益，Autoware 文档明确低速下分离更易维护 |
| **vehicle_cmd_gate 指令门控** | `cmd_gate` 安全限幅链（§8.7） | 所有控制指令过同一安全闸，责任边界清晰 |
| **MRM（最小风险机动）与 route_selector 双路由**（正常路由与 MRM 路由同接口、按状态分发） | 降级链的路由化表达：正常巡检路由 / 返航路由 / 就近停车路由 | 降级不是 if-else 补丁而是与主流程同构的一等公民 |
| velocity_smoother 的 **jerk 受限前后向速度平滑** | speed_profile_gen 核心算法直接借用 | 梯形/S 曲线生成有成熟参考实现可对照验证 |

**舍（及理由）：**

| 不引入 | 理由 |
|--------|------|
| Lanelet2 地图体系 | 其车道几何/拓扑机制为道路设计；轨道拓扑简单得多，自研 RailMap（§8.4）YAML 即可，省去整套地图工具链依赖 |
| LiDAR + NDT/ICP 配准定位 | 无激光雷达配置预算；隧道无高精点云先验图 |
| Nav2 / 自由空间规划器 | 导向轮机械约束下不存在"路径选择"自由度，自由空间规划是负资产 |
| Autoware 整体构建（数百包依赖树） | 维护成本远超收益；只抄设计与代码片段，不 fork 仓库 |
| 横向 MPC 转向控制 | 机械上无转向执行器 |

### 8.2 Autoware 参考架构速览与本项目的降维映射

Autoware 规划栈数据流（官方文档口径）：`Mission Planner 在 Lanelet2 路由图上算出 Route（仅拓扑，latch 发布）→ Behavior Path Planner 场景模块生成参考 Path（~1m 间隔）+ 可行驶区域 → Behavior Velocity Planner 按交规插入减速/停车约束并输出 StopReason → Obstacle Stop/Cruise 处理动态障碍 → Motion Velocity Smoother 做 jerk 受限平滑得到 Trajectory（0.1s 间隔）→ Control 的 trajectory_follower 横纵分离跟踪 → Vehicle Interface 下发底盘`。

### 8.4 RailMap：类 Lanelet2 的轨道拓扑图

Lanelet2 把道路表达为"可行驶通道的有向图"；轨道场景把"通道"退化为"区段"，"路口"退化为"道岔"。自研 YAML 格式：

```yaml
# rail_map_X线_down.yaml —— 出库前载入, 双人复核
meta:    {line: "X", direction: down, rev: 20260825}
markers:                       # 标号牌锚点表(首跑建图产物, OCR 训练真值)
  - {id: "K12",   s_mm: 12000000}
  - {id: "K12+5", s_mm: 12500000}   # 若存在半公里牌则加密
segments:                      # 区段 = 图的边
  - id: seg_120
    from: "K12"      to: "T01_pre"
    v_limit_kmh: 5.0
    ds_trigger_m: 4.0
    imaging: {profile: rigid_a, elev_deg: 35, lamp_pct: 80}
  - id: seg_121
    from: "T01_pre"  to: "K13"
    v_limit_kmh: 5.0
turnouts:                      # 道岔 = 分叉边(带台账属性)
  - id: T01
    at_s_mm: 12300000
    branches: {normal: seg_121, reverse: null}   # 本次不走的岔向置 null
    expected: normal            # 台账常态开通位
    pre_stop_before_m: 20
    crawl_kmh: 1.0
zones:                         # 特殊区(弯道自动加密触发已在配方内)
  - {from: "K12", to: "K12+5", kind: curve, v_limit_kmh: 1.5, ds_div: 4}
```

- `route_planner` 的职责 = 当日任务区段列表 × RailMap → `Route1D`（校验连通性、展开道岔顺序）；对应 Autoware mission_planner"在路由图上做最短路"的最简版（本场景通常就是线性遍历，图搜索保留以支持换轨往返）；
- 地图版本化管理：文件带 rev，加载时打印摘要供双人核对；blackbox 记录当日所用 rev。

### 8.5 定位栈：1D EKF + 视觉锚点更新

Autoware 用 `ekf_localizer` 融合 IMU/里程计与 NDT 位姿；本场景状态量只有里程 `s`，形式化为标量 EKF + 慢变比例因子估计：

```
状态:  x = [s, k̂]      s=里程(m), k̂=编码器比例因子(标称1.0, 慢变)
预测(每 ΔN 脉冲):   s⁻ = s + k̂·ΔN·g ;   P⁻ = P + Q
更新(z = 标牌里程, R = f(ocr_conf)):  K = P⁻/(P⁻+R)
                                     s ← s⁻ + K(z − s⁻) ;  P ← (1−K)P⁻
k̂ 修正(两锚点间):  k̂ ← LS滑窗( Σz_i / Σ脉冲折算 ) , 变化率超阈告警(打滑/轮磨损)
兜底: 两锚点之间用等间距结构特征(电缆支架/板缝)做视觉测距微校正(可选开关)
```

- 对应关系：`encoder_node`≈车轮 odometry 源，`marker_reader`≈yabloc 式"视觉特征→绝对位置"修正源（yabloc 用相机匹配矢量地图定位，我们用 OCR 匹配标牌台账，思想同源：**绝对参考离散校正连续推算**）；
- `localizer` 输出 `/pose_1d @100Hz`（含协方差），全下游统一消费该话题而非各自读编码器——**单一真源原则**；
- OCR 置信度低于阈值 → 该观测不进 EKF，仅记日志并标记"待校正段"。

### 8.6 规划栈：停止约束插件 + jerk 受限速度曲线

**(a) stop_point_manager——对标 behavior_velocity_planner 的插件框架：**

```cpp
// 每个插件 = 一个约束源, 继承统一接口(仿 Autoware scene_module_interface)
class StopConstraintPlugin {
 public:
  virtual std::vector<StopConstraint> evaluate(const PlanContext&) = 0;
  // PlanContext: pose_1d, route, obstacles, window_remaining, loc_cov...
};
// 注册于 default_preset.yaml —— 与 Autoware 的模块启停方式同构
stop_plugins: [obstacle_stop, turnout_stop, window_time_return, loc_lost_stop, recap_slow_zone]
```

| 插件 | 约束逻辑（输出 StopConstraint） |
|------|------------------------------|
| obstacle_stop | 前方障碍距离 d → 停止点 s_obs − 制动裕量（对应 autoware obstacle_stop_planner） |
| turnout_stop | 道岔预告点 → 强制爬行限速；岔前停车点 → v=0（对应 intersection 类场景模块） |
| window_time_return | 天窗剩余时间 < 返航耗时×1.5+缓冲 → 在当前位置插入"立即折返"事件（事件型约束） |
| loc_lost_stop | 定位协方差超阈持续 → 停车约束 + 告警原因 LOC_LOST |
| recap_slow_zone | 质检模糊段 → 该区间限速减半并标记复拍 |

**(b) speed_profile_gen——对标 motion_velocity_smoother：**

- 输入 `/path_1d`（限速包络 + 停止点），输出 `/trajectory_1d`（0.1s 间隔 s-v-a 列）；
- 算法：**前向传播限制加速、反向传播限制制动距离、再施加 jerk 上限平滑**——与 Autoware jerk constrained velocity planning 同型，代码量小（~500 行）且有官方实现可对照回归测试；
- 触发时机：约束集变化（新停止点/进入新区段）或每 2 s 重算，非每周期重算（低频规划 + 高频跟踪的分工）。

### 8.7 控制栈与车辆接口

```
/trajectory_1d ──▶ longitudinal_controller(PID + 速度前馈, 50Hz) ──▶ /control_cmd
                                                                        │
/teleop_cmd(手柄, 最高优先级) ─────────────────────────────┐             ▼
各区段硬限速(RailMap) ────────────────────────────────────┤      ┌────────────┐
温控降额(power_guard/thermal) ────────────────────────────┼─────▶│  cmd_gate  │──▶ chassis_driver(CAN)
断电预警(power_event) → 冻结输出 ─────────────────────────┤      │ min()合成  │
BT 层使能位(AUTO/TELEOP/HALT) ────────────────────────────┘      └────────────┘
```

- **cmd_gate 是唯一允许产生电机指令的节点**（对应 Autoware vehicle_cmd_gate 的"指令必经之门"模式），合成规则 = 取各来源最小值，任何一路失效默认 0；
- 横向不做闭环（导向轮机械导向），接口保留 `lateral_cmd` 字段占位——若后续换差速纠偏底盘可直接启用（借鉴 trajectory_follower 横纵分离接口）；
- 底盘 MCU 内环（电流环 ~200Hz）属硬件范畴，`chassis_driver` 只下发 v/a 目标与读取反馈。

### 8.8 时序预算

| 回路 | 频率 | 说明 |
|------|-----:|------|
| BT mission_manager | 1 Hz | 状态迁移/阶段判断（事件驱动为主，周期巡视为辅） |
| stop_point_manager 插件求值+合成 | 10 Hz | 障碍/协方差等输入的变化响应 |
| speed_profile_gen | 事件触发 + 0.5 Hz 兜底 | 约束未变不重算 |
| longitudinal_controller | 50 Hz | 跟踪 Trajectory1D |
| localizer EKF 预测 | 100 Hz（脉冲驱动） | 更新随锚点事件 |
| cmd_gate | 50 Hz | 直通转发+限幅 |
| 底盘电流内环 | ~200 Hz | MCU 固件（硬件范畴） |

ROS2 实现注意：控制回路用单线程 executor + 绑核（tier4 sensor_trigger 的绑核经验）；图像大流量话题与控制话题分容器运行，避免回调队列互扰；FastDDS SHM 单机通信（Orin-ROS 已验证配置）。

### 8.9 任务层（BT）与连续控制层的职责切分

| | 任务层 BehaviorTree.CPP（1 Hz） | 连续控制层 AD 栈（10–100 Hz） |
|--|--|--|
| 职责 | 离散决策：阶段推进、道岔子流程编排、复拍任务、异常处置流程 | 连续决策：限速包络、速度曲线、跟踪控制 |
| 输出 | `/mission_goal`（目标区段）、模式切换、配方切换 | `/trajectory_1d`、`/control_cmd` |
| 类比 | Autoware 之上的车队调度/FMS + scenario 选择 | Autoware planning+control 主体 |

- 道岔通过 = BT 一个子树（`预减速→停车→核验→步进→确认→恢复`），其中"步进"通过向 speed_profile_gen 注入临时停止点序列实现，**复用同一运动管线而非旁路直控**；
- 降级三路由由 `mrm_manager` 表达（借鉴 Autoware route_selector 正常/MRM 双路由同接口分发）：`NORMAL_ROUTE / RETURN_ROUTE(返航) / HALT_IN_PLACE(就近停车)`，BT 按 power/loc/window 事件切换路由而非散落 if-else。

### 8.10 分阶段对标落地计划

| 步骤 | 内容 | 对标物 |
|------|------|--------|
| S1 | 消息定义冻结（§8.3 契约）+ RailMap schema + rail_map_server | Autoware 接口文档 |
| S2 | 最小闭环：encoder→localizer→手写梯形速度曲线→cmd_gate→底盘台架 | trajectory_follower 设计文档 |
| S3 | stop_point_manager 插件框架 + 前 2 个插件（obstacle/turnout） | behavior_velocity 插件机制 |
| S4 | speed_profile_gen 替换手写曲线（jerk 受限）+ 回归对比 | motion_velocity_smoothen 实现 |
| S5 | 全部 5 插件 + mrm_manager + BT 子树接入 | route_selector/MRM 概念 |
| S6 | 仿真回放：bag 数据 + 伪底盘仿真器（仿 simple_planning_simulator）离线回归每晚任务 | simple_planning_simulator 思想 |

> 每步的验收标准都是"与上一实现的轨迹/速度曲线做数值回归对比"，防止重构引入隐性回归——这是借鉴成熟开源栈最大的隐性收益：**每一步都有参照答案**。

### 8.11 Tier 2 — 语义增强层（低成本增值，建议 M3 后叠加）

- **车载小 VLM（量化 2B–4B，Qwen3-VL 级）离线/低频使用**：
  - 收工时本地生成**巡检日报草稿**（当日区段、里程覆盖、异常统计的自然语言摘要）；
  - 对 online_qc 标记的可疑帧做二次语义判读（"疑似渗漏痕迹/疑似异物"，仅作人工复核排序建议，不进入正式预警链）；
- **自然语言任务接口**（库内有屏场景）："今天扫 X 区段，道岔 K12+300 后换轨" → 解析为任务配方草案，人工确认后下发。降低现场操作门槛。
- 算力可行性：Orin 64GB 跑 4bit 量化 2–4B VLM 做分钟级离线任务无压力（Orin-ROS 已实证同平台 GPU 优化方法论）。

### 8.12 Tier 3 — VLA 端到端策略（研究储备，不建议进安全链）

- **动机**：道岔通过、障碍处置等目前依赖规则+人工的场景，长期可用模仿学习获得更平滑策略；VLA 的语言条件化也便于"指令式"扩展新行为。
- **技术路线**（对齐当前开源生态）：
  1. **数据引擎**：日常遥控/人工处置过程全量录制成 LeRobot 数据集（图像+里程+动作+语言标注）——GR00T 官方工作流要求每任务 50–100 条演示起步，本项目每晚作业天然积累数据；
  2. **微调底座**：OpenVLA-7B（LoRA）或 GR00T N1.x / π0（OpenPi）任选其一做试点；驾驶域思想参考 UniDriveVLA 的专家解耦与 OneVL 的 latent CoT 时延优化；
  3. **部署边界**：VLA 输出仅作为"建议动作"送 BehaviorTree 仲裁层，经速度/限界/急停硬约束过滤后才可执行——**端到端模型永不直接驱动电机**（安全认证现实约束）。
- **诚实的风险评估**：VLA 泛化到未见过的道岔形态/异物类型不可证；推理时延（秒级）不满足紧急避障；因此其在可见未来的价值点是"低频复杂决策建议 + 数据资产沉淀"，而非替代 Tier 1。

## 10. 安全要点（控制程序职责范围内）

1. **硬件安全链独立于软件**：急停按钮、防撞条、轨道端限位直接断动力；软件 ESTOP 仅是补充；
2. 限界合规由机械方负责，控制程序的职责是**不越过软件速度/加速度包络**，并在升降桁架展开态限制速度档；
3. 请销点制度对接：任务配方的作业时间窗与业主批准的天窗点一致，window_timer 强制执行；
4. 人员协同：声光警示常开；TELEOP 模式优先级永远高于 AUTO（模式切换开关硬件保持）；
5. 数据虽不加密，但拔盘交接需登记（盘号-日期-区段清单），防止数据资产混乱。
